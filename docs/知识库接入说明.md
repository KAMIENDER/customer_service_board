# 知识库接入说明

## 结论

`AK/SK` 只能放服务端。  
前端不负责签名，也不要拿签名头去直连火山接口。正确做法是：

- 前端页面调用你自己的代理服务
- 代理服务读取环境变量里的 `AK/SK`
- 代理服务内部生成火山 OpenAPI 鉴权头并发起请求

当前仓库里已经有三层：

- 前端 provider：
  [js/knowledge-base-provider.js](/Users/hejiadong/project/customer_service_board/js/knowledge-base-provider.js)
- 火山签名与请求工具：
  [server/volcengine-openapi.js](/Users/hejiadong/project/customer_service_board/server/volcengine-openapi.js)
- 可部署的代理入口：
  [server/app.js](/Users/hejiadong/project/customer_service_board/server/app.js)

## 现在怎么跑

### 1. 准备环境变量

复制一份 [.env.example](/Users/hejiadong/project/customer_service_board/.env.example) 为 `.env`，至少补这几个值：

```bash
PORT=38888
CORS_ORIGIN=http://localhost:3000
VOLC_ACCESS_KEY_ID=你的AK
VOLC_SECRET_KEY=你的SK
VOLC_REGION=cn-beijing
VOLC_OPENAPI_SERVICE=air
VOLC_OPENAPI_BASE_URL=https://open.volcengineapi.com
```

### 2. 本地开发

终端 1：

```bash
npm run dev
```

终端 2：

```bash
npm run dev:api
```

### 3. 生产部署

```bash
npm run build
npm start
```

`npm start` 会同时提供：

- `/api/*` 代理接口
- `dist/` 下的静态页面

这样线上只需要一个 Node 服务。

## 代理接口

### 健康检查

```bash
GET /api/health
```

返回当前代理是否已配置凭证。

### JSON 请求代理

```bash
POST /api/volc/request
Content-Type: application/json
```

请求体示例：

```json
{
  "pathname": "/your/openapi/path",
  "method": "POST",
  "region": "cn-beijing",
  "service": "air",
  "body": {
    "foo": "bar"
  }
}
```

### 知识库集合列表

已经单独封装了一个业务路由：

```bash
POST /api/knowledge-base/collections
Content-Type: application/json
```

请求体：

```json
{
  "brief": false
}
```

`project` 现在按官方接口处理为选填；不传时会返回账号下可访问的全部集合。

当前已经验证过这个路由底层对应的真实火山接口：

- Host: `api-knowledgebase.mlp.cn-beijing.volces.com`
- Path: `/api/knowledge/collection/list`
- Region: `cn-beijing`
- Service: `air`

### 知识库详情

已经单独封装了一个业务路由：

```bash
POST /api/knowledge-base/collection-info
Content-Type: application/json
```

请求体支持两种方式：

```json
{
  "name": "colorlomon_online",
  "project": ""
}
```

或：

```json
{
  "resource_id": "kb-447701b548a38b68"
}
```

当前已经验证过这个路由底层对应的真实火山接口：

- Host: `api-knowledgebase.mlp.cn-beijing.volces.com`
- Path: `/api/knowledge/collection/info`
- Region: `cn-beijing`
- Service: `air`
- `name + 空 project` 可正常命中卡洛美知识库

### 文件列表

这个项目建议直接暴露文件层，不让前端感知知识库集合层。

已封装业务路由：

```bash
POST /api/files/list
Content-Type: application/json
```

请求体示例：

```json
{
  "resource_id": "kb-447701b548a38b68",
  "limit": 10,
  "return_token_usage": true
}
```

或者：

```json
{
  "collection_name": "colorlomon_online",
  "project": "default",
  "limit": 10,
  "filter": {
    "doc_id_list": [
      "_sys_auto_gen_doc_id-3649169154633492992"
    ]
  }
}
```

说明：

- 代理内部调用火山真实接口 `/api/knowledge/doc/list`
- 如果传 `collection_name` 但没传 `project`，代理会自动补成 `default`
- 如果已知知识库 `resource_id`，优先建议直接传 `resource_id`
- 已验证卡洛美知识库的 `resource_id` 查询可正常返回文档列表

### 文件上传添加

已封装业务路由：

```bash
POST /api/files/upload
Content-Type: multipart/form-data
```

上传字段：

- `files`: 多文件

代理实现方式：

- 页面先把文件传到你自己的服务端
- 服务端生成一个临时公开地址
- 再调用火山文档添加接口 `/api/knowledge/doc/add`
- 当前实现使用 `add_type: "url"`

注意：

- 火山会主动拉取这个文件地址，所以必须配置 `PUBLIC_BASE_URL`
- `PUBLIC_BASE_URL` 必须是外网可访问地址，`localhost` 不可用
- 默认知识库目标由服务端环境变量控制，不向前端暴露

### Multipart 请求代理

```bash
POST /api/volc/request-multipart
Content-Type: multipart/form-data
```

表单字段约定：

- `pathname`: 必填，火山 OpenAPI 路径
- `region`: 选填
- `service`: 选填
- `params`: 选填，JSON 字符串
- `fields`: 选填，JSON 字符串，会一起拼进 multipart body
- 文件：直接随表单上传，字段名会原样透传

### 调试签名结果

默认关闭。只在本地排查时把 `.env` 里的 `ENABLE_VOLC_SIGN_DEBUG=1` 打开：

```bash
POST /api/volc/signature
```

返回的是脱敏后的签名头，用来确认本地签名是否生成成功，不建议在线上开启。

## 代码里怎么调

```js
import { requestVolcOpenApi, requestVolcOpenApiMultipart } from './server/volcengine-openapi.js';

const data = await requestVolcOpenApi(
  {
    pathname: '/your/openapi/path',
    method: 'POST',
    region: 'cn-beijing',
    body: {
      foo: 'bar'
    }
  },
  {
    accessKeyId: process.env.VOLC_ACCESS_KEY_ID,
    secretKey: process.env.VOLC_SECRET_KEY
  }
);
```

## 跟知识库页面怎么衔接

现在 [js/knowledge-base.js](/Users/hejiadong/project/customer_service_board/js/knowledge-base.js) 已经支持两种模式：

- 没配 `VITE_KB_PROXY_BASE_URL`：本地演示模式
- 配了 `VITE_KB_PROXY_BASE_URL`：远端代理模式

但要注意，当前前端 provider 约定的是业务化接口：

- `GET /entries`
- `POST /entries`
- `POST /documents`
- `DELETE /entries/:id`

这层“知识库业务接口”还需要你根据火山知识库的真实 API 路径和字段，再在代理服务里补一层适配。  
也就是说：

- [server/app.js](/Users/hejiadong/project/customer_service_board/server/app.js) 现在已经把“签名和安全问题”处理掉了
- 下一步只剩“把火山知识库具体接口映射成前端需要的 CRUD 结构”

## 部署建议

- 前后端同域部署最省事，浏览器不会再碰到跨域问题
- `AK/SK` 只放环境变量，不要写进前端代码或 git 仓库
- 你之前贴出来的凭证已经暴露过，建议尽快在火山控制台轮换
